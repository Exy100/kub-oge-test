# Каталог игровых объектов

Названия, описания и общие свойства реализованных объектов задаются в `catalog/`.
Игра обращается к ним через `catalog.get(id)`. Это единая точка доступа, а не один
большой файл. Каталог не зависит от Three.js, DOM или состояния игрока.

## Что где хранить

- `catalog/resources.js`: строительные материалы, бит и байт; названия, описания,
  значки, цвета строительных кубов и номера ячеек материалов.
- `catalog/tools.js`: предметы-орудия, пока жезл сбора.
- `catalog/trees.js`: разновидности деревьев, палитры, размеры частей и столкновения.
- `world/trees.js`: общий способ создания моделей деревьев. Материалы переиспользуются.
  Анимации и сложные модели других предметов остаются в своих модулях, например
  `gathering-wand.js` и `byte-model.js`.
- `locations/*.js`: ID и название локации, тексты задания, размещение деревьев
  через `objectId`, координаты, масштаб и отражение. Остальная геометрия локаций
  и размещение кузницы пока остаются в `game.js` и `forge.js`.
- `progression.js`, `player-inventory.js`, `forge-state.js`: изменяемое состояние —
  запасы, экипировка, построенные блоки и прогресс.

В каталог пока не входят декорации без отдельной игровой сущности (трава, облака,
основание острова), редактор внешности и варианты навигатора с собственными каталогами.
Запланированные, но ещё не реализованные враги и оружие остаются в дизайн-документах.
Добавлять их в рабочий каталог следует вместе с реализацией.

## ID и экземпляры

`tree.island` обозначает разновидность дерева. На острове могут стоять десятки
экземпляров этой разновидности с разными координатами. Определение неизменно;
текущее здоровье или другое состояние экземпляра нельзя записывать в каталог.
У моделей ссылка на определение хранится в `userData.objectId`.

Существующие ID `wand`, `bit`, `byte`, `material-0`…`material-5` сохранены.
Название можно менять свободно, ID — только с миграцией всех ссылок и сохранений.
Новые ID следует задавать осмысленно, например `weapon.blocker`. Числовые слоты
материалов также нельзя переставлять: их использует текущая строительная система.
Полного сохранения игрового прогресса между перезагрузками пока нет; эта структура
позволяет будущим сохранениям хранить ID и состояние вместо копий текстов.

Инвентарь принимает только зарегистрированные предметы и разрешает ID через каталог при каждом чтении: старые копии
названий и категорий не могут переопределить актуальные данные. Название, описание,
категория и значок для интерфейса доступны через `itemStack(id, quantity)`.
Подсказки инвентаря, снаряжения и панели материалов используют эти данные.
Навигатор озвучивает краткую цель из поля `quest.brief` в файле локации.
Записывайте её одной фразой. Текущий прогресс отображается в панели отдельно.

## Как добавить объект

1. Добавить определение в соответствующий файл каталога с уникальным ID, `type`,
   `name`, `description` и свойствами своей категории. Для новой категории создать
   отдельный файл, подключить его в `catalog/index.js` и добавить проверку её схемы
   в `catalog/registry.js`.
2. Для разновидности дерева достаточно указать палитру и части, а затем добавить
   размещение с этим `objectId` в нужную локацию. Отдельный класс не требуется.
3. Если нужен новый способ поведения или отрисовки, добавить модуль реализации.
   Счётчики, здоровье и анимационное время хранить в состоянии экземпляра.
4. Запустить `node --test tests/*.test.mjs`. Проверки каталога также выполняются при
   его загрузке: повторяющиеся ID, неверные параметры и ссылки локаций вызывают
   понятную ошибку с ID объекта или локации.

`node tests/browser-catalog.cjs` проверяет распространение изменений каталога:
в тестовом ответе сервера меняются названия, описание и цвет, а затем проверяются
мир, панель материалов, инвентарь, снаряжение и диалог перезапуска. Исходные файлы
при этом не изменяются. `node tests/browser-story.cjs` проверяет игровой маршрут.

## Рост проекта

Категории можно дробить на подкаталоги без изменения способа обращения по ID.
Когда появятся переводы, тексты можно вынести в языковые словари, сохранив ID объектов.
Большие модели и текстуры стоит загружать отдельно по необходимости; каталог хранит
их описание и ссылки, а не создаёт все ресурсы при импорте.

Markdown объясняет правила и решения. Ручную копию списка названий и характеристик
в нём вести не нужно. Если понадобится справочник всех объектов, его следует
генерировать из каталога, чтобы он не расходился с игрой.
